# Numeric-recall pilot: does automatic figure protection change task outcomes?

Per `docs/BENCHMARK_PROTOCOL.md`'s Family B procedure. The first Family B
pilot (`experiments/family_b_pilot/`, ADR-0011) hit a 100% success ceiling
on both its tasks — locating a one-line code fix was never hard enough to
tell two conditions apart. This pilot corrects that: it tests the
financial-figure protection rule added in ADR-0012 under a constraint
specifically designed to make naive context handling fail, not merely
possibly fail.

**Status: complete.** 10 real trials (5 per condition), each scored by
exact string comparison against a fixed ground truth — never by trusting
the agent's own report. Result: `likely_real_difference` in both
directions, noise floor `[0.0, 0.0]` for `naive` and `[1.0, 1.0]` for
`verity`, with zero overlap between them.

## The fixture

`raw_log.json` (generated by `generate_fixture.py`, not hand-edited) is a
45-message synthetic support conversation: an agent reviewing case #7788
states the customer's account number and amount owed once, in message 3,
with no `verity:critical` marker — testing *automatic* protection, not
manual tagging. A decoy — a different account number and amount,
explicitly attributed to a past, unrelated case (#4521) — appears past the
midpoint. ~40 filler tool-output messages pad the log to 2,016 tokens.

## The two conditions

Both start from the identical raw log and the identical token budget
(800). Neither condition is a live agent using tools — the **harness**
(`prepare_contexts.py`) prepares each condition's context up front, so the
comparison is about context *preparation*, not agent tool-choice:

- **`naive`**: the log truncated to the most recent 800 tokens, keeping
  messages from the end backward. This mirrors what an unmanaged sliding
  context window actually does when it fills up — evict the oldest
  content first — which is exactly what endangers a figure mentioned once,
  early. Result: the target figure (message 3) is evicted; the decoy
  (message ~24) survives, attributed to a closed, unrelated case.
- **`verity`**: the same log and the same 800-token budget, processed
  through `verity context --budget 800`. The financial-figure rule
  (ADR-0012) marks *both* the target and the decoy figures CRITICAL — both
  survive, along with the surrounding sentences needed to tell them apart
  (`"case #4521 ... closed and unrelated to #7788"`).

This is a stronger design than "give one condition tools and not the
other": an agent handed the raw, unmanaged file would trivially match or
beat `verity` on recall, since pruning can only remove information, never
add it. Constraining both conditions to the same budget, prepared two
different ways, is what makes the comparison mean something.

Each trial received only its condition's prepared text and this question,
verbatim from the log's final message: *"what is the exact account number
and total amount owed for the CURRENT case (#7788) — not any previously
referenced case?"* — with an explicit instruction to say "INSUFFICIENT
INFORMATION" rather than guess.

## Method

5 independent trials per condition. Scored `{"success": 1.0}` only on an
**exact** match of both the account number and the amount against
`ground_truth.json`; anything else (including a plausible-sounding wrong
answer, or an honest "insufficient information") scores `0.0`. Verified
directly against each trial's raw response — never inferred from the
trial's own framing of its answer as correct.

## Result

| Condition | 5 trials | Noise floor | Between-config mean | Conclusion |
|---|---|---|---|---|
| `naive` (within) | 0/5 exact matches | `[0.0, 0.0]` | 1.0 (verity) | `likely_real_difference` |
| `verity` (within) | 5/5 exact matches | `[1.0, 1.0]` | 0.0 (naive) | `likely_real_difference` |

All 5 `naive` trials answered `INSUFFICIENT INFORMATION` for both fields —
correctly declining to guess, since the target figure was in fact absent
from what they were given, and notably **not** reporting the decoy as if
it were the answer. All 5 `verity` trials reported the exact correct
account number and amount, letter- and digit-for-digit. Reproduce:

```bash
python3 generate_fixture.py
python3 prepare_contexts.py --budget 800
verity noise-floor naive_results.json verity_results.json --metric success
```

## Known limitations of this pilot, stated up front

- **One fixture, one figure, one budget.** This tests exactly the
  mechanism ADR-0012 added — an unmarked financial figure, evicted by
  tail-truncation, protected by the new classification rule — not a
  general claim about numeric recall under every possible context
  pressure or a different budget.
- **The `naive` baseline is one specific, real failure mode** (tail
  truncation), not the only way an unmanaged context could handle
  overflow. A different naive strategy (head truncation, mid-truncation,
  lossy summarization) would fail differently, and possibly not at all —
  head truncation, in particular, would have *kept* this figure by
  accident, for reasons that have nothing to do with the figure's
  importance.
- **The zero/zero and one/one noise floors are a ceiling in the good
  direction**, not evidence of no variance at all — a single-turn
  recall-or-decline task with an explicit "say so if uncertain"
  instruction is close to deterministic for a capable model given either
  input; a harder or more ambiguous question could show real within-
  condition variance that this pilot's task was too clean to surface.
- **This is a recall task, not a live agent workflow.** Nothing here tests
  whether an agent actively managing its own context (deciding when to
  call `verity context`, when to note a fact, when to check its own prior
  claims) gets the same benefit in a multi-turn session — only whether a
  correctly-prepared context is easier to answer from than an incorrectly
  managed one, which is the mechanism's design claim, not the full product
  claim.
